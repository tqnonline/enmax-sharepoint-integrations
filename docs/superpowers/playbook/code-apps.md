# Code Apps

This file covers Power Apps **Code Apps** — the React/TypeScript app type that runs inside a Power Apps iframe and communicates with Dataverse via generated services. It is distinct from canvas apps and model-driven apps. As a skill, this would be loaded when an agent needs to scaffold a screen, fix a build issue, author tests, or debug a data-fetching problem.

For naming conventions see [naming-conventions.md](./naming-conventions.md). For server paging background see [dataverse-foundation.md](./dataverse-foundation.md).

---

## Stack

| Layer | Technology |
|-------|-----------|
| Framework | React 18 |
| Language | TypeScript (strict mode) |
| UI components | Fluent UI v9 (`@fluentui/react-components`) |
| Styling | Griffel via Fluent UI `makeStyles` |
| Data fetching | TanStack Query (React Query) v5 |
| Routing | React Router v6 with `createHashRouter` |
| Build | Vite |
| Testing | Vitest + React Testing Library + MSW v2 |
| Validation | Zod v4 |
| Push tool | `@microsoft/power-apps` (npm CLI) |

**Use `createHashRouter`, not `createBrowserRouter`.** Code Apps are served from a CDN URL with a path prefix; the browser router breaks under that URL structure. Hash routing (`#/path`) survives CDN serving.

## power.config.json — Data Sources

`power.config.json` in the app root maps the Code App to its Dataverse environment and declares which tables it uses:

```json
{
  "environmentId": "<env-guid>",
  "appId": "<app-guid>",
  "databaseReferences": {
    "default": {
      "cds": {
        "dataSources": {
          "pub_reservations": {
            "entitySetName": "pub_reservations",
            "logicalName": "pub_reservation",
            "isHidden": false
          },
          "systemusers": {
            "entitySetName": "systemusers",
            "logicalName": "systemuser",
            "isHidden": false
          },
          "teams": {
            "entitySetName": "teams",
            "logicalName": "team",
            "isHidden": false
          }
        }
      }
    }
  }
}
```

**Every table the app reads or writes must appear here** — including `systemusers` and `teams` (needed for auth/role resolution). Omitting a table causes the generated service to throw at runtime.

`power.config.json` is generated by the deploy script per environment (`Publish-PpCodeApp`). Do not commit environment-specific values (environment ID, app ID) — commit a template and generate on deploy.

## Rule 15 — Code Apps Cannot Read Environment Variables

**Code Apps cannot read Dataverse environment variables.** This is a platform constraint, not a configuration choice. Environment variables are only accessible to Power Automate flows, model-driven apps, and canvas apps.

**The correct alternative: an App Configuration table.** Create a table with a string key column (`pub_key`) and a value column (`pub_value`) plus a value type column (`pub_valuetype`). The Code App reads all rows from this table at startup via a `useSuspenseQuery` hook and provides them through a React context or hook.

### App Configuration table schema

```
pub_appconfig
  pub_key        (String, required, primary name) — configuration key
  pub_value      (Memo)                           — value as string
  pub_valuetype  (Choice: 1=boolean, 2=integer, 3=string/GUID)
  pub_description (Memo)                          — human note
```

### App Configuration usage pattern

```typescript
// AppConfigSchema.ts
import { z } from "zod";

export const AppConfigSchema = z.object({
  RequireApproval: z.boolean().default(false),    // boolean, code 1
  PageSize: z.number().int().default(10),          // integer, code 2
  AdminTeamId: guidSchema.optional(),              // GUID, code 3
});

export type AppConfig = z.infer<typeof AppConfigSchema>;

// useAppConfig.ts
export function useAppConfig(): AppConfig {
  const { data } = useSuspenseQuery({
    queryKey: ["appconfig"],
    queryFn: fetchAppConfig,
  });
  return AppConfigSchema.parse(data);
}
```

Use `.default(...)` on every schema field so environments that haven't pushed a row yet still boot without throwing a validation error.

Config rows are pushed to Dataverse via the deploy script. The value type codes are **integers** (1/2/3), not strings — a common silent bug in MSW test handlers.

> **Worked example (this repo):** Table `enmax_autocadappconfig`. Key fields only: `enmax_acdnkey`, `enmax_acdnvalue`, `enmax_acdnvaluetype`. There is no `enmax_acdnname` field — including it in a POST body causes `"Invalid property 'enmax_acdnname'"`.

## Auth and Role Resolution

`getContext()` from `@microsoft/power-apps/app` returns the authenticated user's identity. Use the `objectId` (Azure AD object ID, same as the `azureactivedirectoryobjectid` column on `systemuser`) to look up the Dataverse user record.

```typescript
import { getContext } from "@microsoft/power-apps/app";

const ctx = await getContext();
// ctx.user.objectId       — AAD object ID
// ctx.user.fullName
// ctx.user.userPrincipalName
// ctx.app.appId
// ctx.app.environmentId
// ctx.host.sessionId      — use for telemetry correlation
```

**Critical:** `getContext()` hangs indefinitely when the app is not running inside a real Power Apps iframe. Local Vite preview (`npm run preview`) always hangs. All e2e tests must run against the deployed app URL.

### Role resolution pattern

```typescript
// Resolution order (fail-closed: Unknown if both queries fail)
// 1. Check system roles — sys admin bypasses team membership
const isSysAdmin = await checkSystemAdminRole(userId);
if (isSysAdmin) return "Admin";

// 2. Check team membership (parallel queries via Promise.allSettled)
const teamMemberships = await queryTeamMemberships(userId);
if (teamMemberships.includes(adminTeamId)) return "Admin";
if (teamMemberships.includes(approverTeamId)) return "Approver";
if (teamMemberships.includes(userTeamId)) return "User";

return "Unknown"; // fail-closed
```

Use `Promise.allSettled` so one failing query does not block the others. Return `null` while the role query is pending to prevent a "checking permissions…" flash. Team IDs come from the App Configuration table (they are GUIDs stored as string/GUID values, type code 3).

## Zod v4 and Dataverse GUIDs

`z.string().uuid()` in Zod v4 enforces RFC 4122 version nibble `[1-8]`. Dataverse GUIDs use version nibble `f` (e.g. `7e7f5cf0-2153-f111-bec7-00224802e55b`) and fail this validation.

Use a custom regex instead:

```typescript
const guidSchema = z.string().regex(
  /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i,
  "Must be a valid GUID",
);
```

## Server Paging with skipToken

Dataverse does not support `$skip` (see [dataverse-foundation.md](./dataverse-foundation.md)). For large grids, use server paging with forward-only cursor tokens.

The correct SDK options interface uses `maxPageSize` and `skipToken` (not `skip`):

```typescript
const result = await MyTableService.getAll({
  filter: "...",
  select: ["pub_name", "pub_state"],
  orderBy: ["createdon desc"],
  maxPageSize: 50,
  skipToken: currentPageToken ?? undefined,
  count: true,
});
// result.skipToken → token for the NEXT page
// result.count     → total record count (requires count: true)
```

**Grid-level token cache:** maintain a `Map<pageNumber, skipToken>` per grid. On "next" pass the cached token for `page + 1`; on "prev" pass the cached token for `page - 1`. When search, filter, sort, or page size changes, clear the entire cache and reset to page 1.

**When to server-page vs client-side:** only large, unbounded shared tables (potentially thousands of records) need server paging. Per-user grids (my items), small config/lookup tables, and grids where computed columns or bulk selection are needed can fetch all records and slice client-side.

## React Query Configuration

```typescript
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      throwOnError: false,  // errors surface per-query, not to error boundary
      staleTime: 30_000,
    },
  },
});
```

**`throwOnError: false`** on the global client is important. With `true`, any failed query throws to the nearest React error boundary, wrapping the entire page in an error state for a single failed data fetch. With `false`, errors surface per-query via the `error` field and can be shown as toasts or inline messages.

Use `useSuspenseQuery` for critical data that the page cannot render without (app config, user identity). Use `useQuery` for non-blocking data with graceful degradation.

### Cross-query invalidation

When a mutation changes state that multiple queries display, invalidate all affected query keys:

```typescript
onSuccess: () => {
  void queryClient.invalidateQueries({ queryKey: ["reservation-drawings"] });
  void queryClient.invalidateQueries({ queryKey: ["reservation-detail"] });
  void queryClient.invalidateQueries({ queryKey: ["checkouts"] });
},
```

Omitting any key leaves stale data (e.g. status badges showing the old state until manual refresh).

## Build Gotchas

### `tsc --noEmit` is a no-op in this project structure

The root `tsconfig.json` uses `"files": []` plus project `references` (pointing to `tsconfig.app.json` and `tsconfig.node.json`). Running `npx tsc --noEmit` on such a tsconfig typechecks nothing and always exits 0 — a false green.

**Always use `npx tsc -b` (build mode)** which resolves project references, or `npm run build` which runs `tsc -b && vite build`.

### Griffel `makeStyles` forbids CSS shorthands

Griffel (the CSS-in-JS engine behind Fluent UI v9) does not support CSS shorthand properties inside `makeStyles` calls. Use longhand properties or inline styles:

```typescript
// Wrong — makeStyles will throw or produce incorrect CSS
header: {
  margin: "8px 16px",          // shorthand
  border: "1px solid red",     // shorthand
  padding: "4px 8px",          // shorthand
},

// Correct — use longhand
header: {
  marginTop: "8px",
  marginRight: "16px",
  marginBottom: "8px",
  marginLeft: "16px",
  borderWidth: "1px",
  borderStyle: "solid",
  borderColor: tokens.colorBrandForeground1,
  paddingTop: "4px",
  paddingRight: "8px",
  paddingBottom: "4px",
  paddingLeft: "8px",
},
```

### No hardcoded colors

All colors must use Fluent UI design tokens. Hardcoded colors break dark theme compatibility.

```typescript
// Wrong
style={{ color: "#ff0000" }}
style={{ color: "red" }}

// Correct
style={{ color: tokens.colorPaletteRedForeground1 }}
style={{ backgroundColor: tokens.colorPaletteRedBackground3 }}
style={{ borderColor: tokens.colorPaletteRedBorderActive }}
```

## Testing

### Unit tests (Vitest + RTL)

```typescript
import { render, screen } from "@testing-library/react";
import { server } from "@/mocks/server";
import { http, HttpResponse } from "msw";
import { createTestWrapper } from "@/test-utils";

// Override handlers for a specific test
server.use(
  http.get("*/api/data/v9.2/pub_reservations*", () =>
    HttpResponse.json({ value: [] })
  )
);

test("renders empty state", async () => {
  render(<MyComponent />, { wrapper: createTestWrapper() });
  await screen.findByText("No items");  // findBy* (async) for data-fetched content
});
```

### MSW handler patterns for Dataverse

```typescript
// List records
http.get("*/api/data/v9.2/pub_mytables*", () =>
  HttpResponse.json({ value: mockRows })
),

// Global Custom Action
http.post("*/api/data/v9.2/pub_MyAction", () =>
  HttpResponse.json({ IssuedNumbers: "101,102,103" })
),

// Entity-bound Custom Action
http.post("*/api/data/v9.2/pub_mytables(*)/Microsoft.Dynamics.CRM.pub_MyAction", () =>
  HttpResponse.json({ NewStatus: 2 })
),

// Config table — type codes must be integers (not strings)
http.get("*/api/data/v9.2/pub_appconfigs*", () =>
  HttpResponse.json({
    value: [
      { pub_key: "RequireApproval", pub_value: "false", pub_valuetype: 1 }
    ]
  })
),
```

### Test overlay flake prevention

Do not test dialog/panel content by driving the full page → OverlayDrawer → modal Dialog navigation chain with `userEvent`. This is load-sensitive and flakes intermittently under the full test suite (parallel CPU contention causes the modal to unmount between query steps).

**Correct approach:** render the dialog component directly with `open={true}` and test it in isolation:

```typescript
// Flaky
render(<MyPage />);
await userEvent.click(screen.getByText("Open Dialog"));
await screen.findByRole("dialog");  // dialog may not be stable under load
await userEvent.type(screen.getByRole("textbox"), "reason");

// Stable
render(<MyDialog open={true} onClose={vi.fn()} />, { wrapper: createTestWrapper() });
await userEvent.type(screen.getByRole("textbox"), "reason");
expect(screen.getByRole("button", { name: "Confirm" })).toBeEnabled();
```

### Playwright (CD only)

`getContext()` hangs without a real Power Apps iframe. Never run Playwright against `localhost` or `npm run preview`.

```typescript
// playwright.config.ts
webServer: process.env.SMOKE_URL
  ? undefined                                    // CD: use deployed URL
  : { command: "npm run preview", url: "http://localhost:4173" },

// All e2e tests
test.describe("My feature @smoke", () => {
  test("loads and shows data", async ({ page }) => { ... });
});
```

Run only during CD via `npx playwright test --grep @smoke`. Do not run in PR CI — there is no live URL.

## Page Layout Conventions

Every page follows a consistent structure:

```typescript
const FADE_UP = {
  from: { opacity: "0", transform: "translateY(8px)" },
  to:   { opacity: "1", transform: "translateY(0)" },
};

const useStyles = makeStyles({
  page: {
    display: "flex",
    flexDirection: "column",
    gap: tokens.spacingVerticalL,       // gap, not marginBottom
  },
  header: {
    paddingLeft: tokens.spacingHorizontalL,
    borderLeftWidth: "4px",
    borderLeftStyle: "solid",
    borderLeftColor: tokens.colorBrandForeground1,
    animationName: FADE_UP,
    animationDuration: "200ms",
    animationFillMode: "both",
  },
});

// JSX
<div className={styles.page}>
  <div className={styles.header}>
    <Title2 as="h1">Page Title</Title2>
    <Text size={300} className={styles.subtitle}>
      One-line description of what this page shows.
    </Text>
  </div>
  {/* tabs, grids, panels */}
</div>
```

Rules:
- Use `gap` on the page container, never `marginBottom` on sections.
- Every page: `Title2 as="h1"` + subtitle `Text size={300}`.
- Brand left border on header: 4px solid `colorBrandForeground1`.
- FADE_UP on header and each tab content pane.
- All spacing via Fluent tokens — never hardcoded pixels for spacing.
- DataGrid columns that close over component state (role, navigate, maps): define with `useMemo` inside the component, not at module level.

For danger actions (delete, force operations):

```typescript
// Trigger button — outline with semantic red, NOT subtle (subtle looks like a link)
<Button
  appearance="outline"
  style={{
    color: tokens.colorPaletteRedForeground1,
    borderColor: tokens.colorPaletteRedForeground1
  }}
>
  Force Check-In
</Button>
```

For dual-mode components (admin vs user context), use an `adminMode?: boolean` prop. The admin guard must precede the ownership guard:

```typescript
interface Props {
  record: MyRecord;
  adminMode?: boolean;
}

export function MyActionsPanel({ record, adminMode }: Props) {
  // Admin guard first
  if (adminMode && (role === "Admin" || role === "Approver")) {
    return <AdminActions record={record} />;
  }
  // Ownership guard second
  if (record.ownerId === currentUserId) {
    return <UserActions record={record} />;
  }
  return null;
}
```

## Step-by-step: Scaffold a New Screen

1. Create `src/features/<feature>/<FeatureName>Page.tsx` with the standard page skeleton (header + FADE_UP).
2. Create `src/features/<feature>/use<FeatureName>.ts` with the React Query hooks that fetch data.
3. Register the route in `src/router.tsx` under `createHashRouter`.
4. Add a data source entry to `power.config.json` for every table the screen reads/writes (if not already present).
5. Add MSW handlers in `src/mocks/handlers.ts` for each new endpoint.
6. Write tests in `src/features/<feature>/<FeatureName>Page.test.tsx` — render directly, mock handlers, use `findBy*` for async content.
7. Run `npx tsc -b` (not `tsc --noEmit`) to verify no type errors.
8. Run `npm test -- --run` to verify all tests pass.
9. Run `npm run build` to verify the production build succeeds.
10. Push to dev: `Publish-PpCodeApp -Environment dev`.
11. Open the live app URL in the browser — `getContext()` works only here.
